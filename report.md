# Анализ безопасности разработанного приложения

## 1. Объект анализа

Анализируется веб-приложение лабораторной работы №3. Приложение реализовано на Python с использованием FastAPI и имеет следующие функции:

- создание, получение, изменение и удаление записей;
- разделение данных на конфиденциальные и неконфиденциальные;
- хранение данных только в оперативной памяти;
- шифрование названия и содержимого конфиденциальных записей;
- веб-интерфейс без регистрации, авторизации и access-токенов.

Исходный код разделён на слои `domain`, `application`, `infrastructure`, `api` и `presentation`. Точка сборки приложения находится в `src/main.py`.

## 2. Защищаемые ресурсы

Основными защищаемыми ресурсами являются:

1. Содержимое конфиденциальных записей.
2. Названия конфиденциальных записей.
3. Ключ Fernet, используемый для шифрования.
4. Целостность записей и корректность CRUD-операций.
5. Доступность приложения и оперативная память процесса.

Для неконфиденциальных записей защита содержимого от чтения не требуется по смыслу задания, однако приложение должно сохранять их целостность и корректно обрабатывать пользовательский ввод.

## 3. Анализ архитектуры безопасности

### 3.1. Разделение ответственности

Архитектура разделяет бизнес-логику и внешние механизмы:

- `src/domain` содержит сущности, типы данных и доменные ошибки;
- `src/application/use_cases.py` реализует правила валидации, шифрования и CRUD;
- `src/infrastructure/in_memory_repository.py` отвечает только за хранение в памяти;
- `src/infrastructure/fernet_encryptor.py` предоставляет механизм шифрования;
- `src/api/routes.py` преобразует HTTP-запросы в вызовы application-слоя;
- `frontend` отвечает за пользовательский интерфейс.

Такое разделение уменьшает риск смешивания бизнес-правил с HTTP-кодом и упрощает отдельный анализ каждого слоя.

### 3.2. Поток конфиденциальных данных

При создании конфиденциальной записи выполняется следующая последовательность:

1. FastAPI принимает JSON-запрос и валидирует его через `DataInput`.
2. Application-слой удаляет пробелы по краям названия и содержимого.
3. Название и содержимое передаются в `FernetEncryptor`.
4. В in-memory репозиторий помещаются ciphertext-значения.
5. Для ответа пользователю данные временно расшифровываются.

Ключ генерируется при запуске в `src/main.py` и не записывается в файл или базу данных. При перезапуске создаётся новый ключ, поэтому старые данные вместе с прежним ключом исчезают.

## 4. Положительные меры защиты

### 4.1. Валидация входных данных

В `src/api/schemas.py` заданы ограничения:

- название не может быть пустым;
- длина названия ограничена 200 символами;
- содержимое не может быть пустым.

Дополнительная проверка выполняется в `DataUseCases._validate()`. Значения очищаются через `strip()`, после чего повторно проверяется отсутствие пустых строк.

Идентификатор записи преобразуется FastAPI в целое число. Для несуществующих записей application-слой формирует `RecordNotFoundError`, который API преобразует в ответ `404 Not Found`.

### 4.2. Шифрование

В `src/infrastructure/fernet_encryptor.py` используется Fernet из библиотеки `cryptography`. Fernet обеспечивает:

- шифрование конфиденциального значения;
- проверку целостности ciphertext;
- генерацию ключа с использованием криптографически стойкого генератора.

Шифруются оба поля конфиденциальной записи: `title` и `content`. Репозиторий не выполняет расшифровку и хранит только строковые ciphertext-значения.

### 4.3. Защита от XSS во frontend

Список записей выводится через `innerHTML`, поэтому прямое помещение пользовательского текста в HTML было бы опасным. Для снижения риска в `frontend/app.js` используется функция `escapeHtml()`, заменяющая символы `&`, `<`, `>`, `"` и `'` на HTML-сущности.

Таким образом, строка вроде `<script>alert(1)</script>` отображается как обычный текст, а не выполняется браузером.

Ошибки выводятся через `textContent`, что также не интерпретирует их как HTML.

### 4.4. Отсутствие постоянного хранения

`InMemoryDataRepository` использует обычный словарь Python. Приложение не подключает SQLAlchemy, SQLite или файловое хранилище. Это уменьшает риск утечки данных через:

- файлы базы данных;
- резервные копии;
- журналы SQL-запросов;
- временные файлы приложения.

Одновременно это означает, что данные теряются при остановке процесса.

### 4.5. Локальный режим запуска

При запуске из `src/main.py` Uvicorn слушает `127.0.0.1`, поэтому приложение не публикуется во внешнюю сеть по умолчанию. Это уменьшает риск удалённого доступа во время демонстрации лабораторной работы.

## 5. Выявленные уязвимости и ограничения

| ID | Проблема | Риск | Оценка |

| S-01 | Отсутствуют аутентификация и авторизация | Любой пользователь, имеющий доступ к адресу приложения, может читать, изменять и удалять данные | Высокий при сетевом запуске; допустимо по условию лабораторной работы |

### 5.1. Отсутствие авторизации

Отсутствие авторизации является осознанным решением, так как пользователь явно исключил окна входа, пользователей и access-токены. Для лабораторной демонстрации на `localhost` это допустимо. Для размещения приложения в локальной сети или интернете такую конфигурацию использовать нельзя.

### 5.2. Ограничение размера содержимого

Сейчас для `content` задано только минимальное ограничение длины. Пользователь может отправить очень большое поле, а приложение сохранит его в словаре и будет возвращать в ответах. Это позволяет исчерпать оперативную память или увеличить время шифрования и расшифровки.

Рекомендуемое улучшение — задать максимальный размер содержимого через `Field(max_length=...)` и дополнительно ограничить размер HTTP-запроса на уровне сервера или reverse proxy.

### 5.3. Данные в памяти

Шифрование защищает значения внутри репозитория, но application-слой обязан расшифровать их перед возвратом в браузер. Поэтому plaintext существует в памяти:

- во время выполнения `_to_view()`;
- внутри объекта HTTP-ответа;
- в структурах сериализации JSON;
- в памяти браузера после получения ответа;
- в возможных временных копиях Python-строк.

После удаления записи ciphertext удаляется из словаря, однако гарантировать немедленное физическое затирание всех копий plaintext в памяти Python нельзя. Это нужно учитывать при анализе дампов.

### 5.4. Многопроцессный запуск

Хранилище является локальным объектом Python и не является общим между процессами. Запуск нескольких worker-процессов приведёт к нескольким независимым словарям записей. Для текущего варианта должен использоваться один процесс приложения.

## 6. Анализ API и frontend

API имеет отдельные маршруты для публичных и конфиденциальных данных. При обращении к маршруту одного типа проверяется, что запись действительно относится к этому типу. Это предотвращает получение записи через неправильную вкладку API.

Ответы ограничены моделями `DataOutput`, поэтому FastAPI не возвращает внутренние поля сущности или служебные объекты.

Frontend не хранит токены и не использует cookies авторизации. Запросы выполняются через `fetch` к тому же источнику, откуда загружена страница.

Основной риск frontend-части связан с использованием `innerHTML`. Текущая функция `escapeHtml()` снижает риск XSS, но при добавлении новых мест вывода необходимо продолжать использовать экранирование или перейти на создание DOM-элементов через `textContent`.

## 7. Рекомендации по улучшению

Для учебного варианта достаточно зафиксировать следующие рекомендации:

1. Ограничить максимальный размер `content`.
2. Добавить rate limiting для API.
3. Добавить строгие security headers и CSP.
4. Не публиковать приложение за пределами `localhost` без авторизации и HTTPS.
5. Использовать один worker при in-memory-хранилище.
6. Добавить журналирование CRUD-операций без записи конфиденциального содержимого в логи.
7. Для production хранить ключ в защищённом хранилище секретов, а не генерировать его при каждом запуске.
8. Рассмотреть отдельный механизм управления жизненным циклом секретов и минимизации plaintext-копий в памяти.
9. Добавить автоматические проверки XSS, валидации и доступа к записям.

## 8. Итоговая оценка

Приложение корректно реализует базовую защиту, необходимую для задания: конфиденциальные данные шифруются перед помещением в оперативное хранилище, публичные данные обрабатываются отдельно, входные значения валидируются, а HTML-вывод экранируется.

Главное ограничение — отсутствие авторизации и защиты памяти. Первое соответствует условию лабораторной работы, но делает приложение непригодным для открытого сетевого использования. Второе является свойством самой задачи: для отображения конфиденциальных данных приложение должно временно хранить расшифрованные значения в памяти, поэтому дамп процесса потенциально может раскрыть исходный текст и ключ шифрования.

С точки зрения учебного задания приложение демонстрирует правильное разделение слоёв, использование криптографического шифрования, обработку пользовательского ввода и основные риски хранения конфиденциальной информации в оперативной памяти.

## 9. Анализ оперативной памяти и процессорного времени

Для измерений был добавлен класс `PerformanceAnalyzer` в файле `src/infrastructure/performance_analyzer.py`. Benchmark-скрипт находится в `scripts/run_performance_test.py`.

Тест выполняет пять независимых запусков. В каждом запуске создаётся новое in-memory-приложение и выполняются следующие этапы:

1. Измерение базового состояния процесса.
2. Создание 100 неконфиденциальных записей.
3. Создание 100 конфиденциальных записей с Fernet-шифрованием.
4. Получение 200 записей с расшифровкой конфиденциальных данных.
5. Обновление 200 записей.
6. Удаление 200 записей.

Исходные строки для записей генерируются самим benchmark-скриптом. Конфиденциальные данные не записываются в лог результатов: сохраняются только технические показатели.

### 9.2. Методика измерения

Для каждой операции используется контекстный менеджер:

```python
with analyzer.measure("create", "confidential", 100000):
    # выполняется измеряемая операция
```

Перед операцией фиксируются:

- текущее время через `time.perf_counter()`;
- процессорное время процесса через `psutil.Process.cpu_times()`;
- RSS процесса через `psutil.Process.memory_info().rss`;
- текущий и пиковый объём Python-аллокаций через `tracemalloc`.

После операции показатели считываются повторно. Разность начального и конечного значения используется для расчёта изменения памяти и процессорного времени.

Реальное время операции рассчитывается так:

```text
elapsed = время_после - время_до
```

Процессорное время:

```text
cpu_time = CPU time после - CPU time до
```

Относительная загрузка процесса рассчитывается приближённо:

```text
cpu_percent = cpu_time / elapsed × 100
```

Этот показатель показывает загрузку процесса относительно одного логического ядра за время конкретной операции. Это не то же самое, что общая загрузка всего компьютера в Диспетчере задач Windows.

### 9.3. Почему CPU может показывать 101–133%

Значения около 101% или 133% не означают, что однопоточный Python-код действительно использовал больше одного ядра. Для коротких операций причиной является погрешность измерения:

1. На Windows процессорное время процесса может предоставляться с дискретностью примерно 15,6 мс.
2. Реальное время операции измеряется более точно и может быть, например, 15,3 мс.
3. CPU time при этом может округлиться до 15,625 мс.

Получается:

```text
15,625 / 15,3 × 100 ≈ 102%
```

Аналогично в предыдущем запуске появлялось значение около 133%, если CPU time округлялся до ближайшего доступного значения, а реальное время операции было заметно меньше. В актуальном запуске на 200 000 удалений получено 101,285%: `CPU time` составил 106,250 мс, а реальное время — 105,759 мс. Разница небольшая и также объясняется точностью системного счётчика и округлением.

Для операций, которые выполняются быстрее одного измерительного интервала, может наблюдаться и обратная ситуация — `0%`, поскольку разность CPU time округляется до нуля.

Поэтому для коротких операций показатели CPU percent нестабильны. Основным показателем в данной работе является `cpu_time_ms`, а `cpu_percent` используется только как приблизительная оценка загрузки процесса. Для повышения точности следует измерять более крупную серию операций и усреднять результат.

### 9.4. Что такое RSS

RSS расшифровывается как Resident Set Size. Это объём памяти процесса, который в данный момент размещён в физической оперативной памяти.

В RSS входят:

- интерпретатор Python;
- загруженные библиотеки;
- объекты приложения;
- словарь in-memory-репозитория;
- ciphertext и расшифрованные строки;
- служебные структуры и буферы процесса.

RSS показывает память всего процесса, а не только размер пользовательских записей. Поэтому значение около 25 МБ не означает, что сами записи занимают 25 МБ.

После удаления объектов RSS может не уменьшиться. Python и операционная система могут оставить выделенные страницы памяти процессу для последующего повторного использования.

### 9.5. Что такое Peak Python

`Peak Python` — это максимальный объём памяти Python-аллокаций, зафиксированный `tracemalloc` во время измеряемой операции.

В отличие от RSS, этот показатель отражает в основном память, выделенную Python-кодом. Он не включает полностью память интерпретатора, native-библиотек и некоторые буферы сторонних расширений.

Поэтому показатели имеют разный смысл:

- RSS — фактическая резидентная память всего процесса;
- текущий `tracemalloc` — активные отслеживаемые Python-аллокации;
- `Peak Python` — максимум отслеживаемых Python-аллокаций во время этапа.

Например, RSS может не измениться после удаления записей, а Peak Python может показывать временные выделения во время расшифровки или создания объектов.

### 9.6. Ограничения эксперимента

Полученные значения зависят от:

- версии Python;
- версии Windows;
- количества логических ядер;
- фоновых процессов;
- состояния памяти и кэшей;
- точности системного учёта CPU time;
- накладных расходов `tracemalloc` и самого анализатора.

Поэтому результаты следует использовать для сравнения этапов между собой в рамках одного запуска, а не как абсолютные характеристики производительности компьютера.

## 10. Анализ дампов оперативной памяти

### 10.1. Цель эксперимента

Целью анализа дампов было проверить, какие данные реально присутствуют в оперативной памяти процесса после создания, обновления и удаления записей.

Для автоматизации был создан скрипт `scripts/run_memory_dump_test.py`. Он запускает отдельный worker-процесс, использующий те же классы `DataUseCases`, `InMemoryDataRepository` и `FernetEncryptor`, что и основное приложение. Дампы создаются через Windows API `MiniDumpWriteDump`, поэтому для эксперимента не требуется отдельная база данных или ProcDump.

Тест использует уникальные контрольные строки:

- публичные данные: `PUBLIC_TITLE_12345`, `PUBLIC_CONTENT_12345`;
- обновлённые публичные данные: `UPDATED_PUBLIC_TITLE_67890`, `UPDATED_PUBLIC_CONTENT_67890`;
- конфиденциальные данные: `SECRET_TITLE_12345`, `SECRET_CONTENT_12345`;
- обновлённые конфиденциальные данные: `UPDATED_TITLE_67890`, `UPDATED_CONTENT_67890`.

### 10.2. Этапы создания дампов

Выполняется следующая последовательность:

1. Создание публичной и конфиденциальной записей.
2. Создание `dump_after_create.dmp`.
3. Обновление публичной и конфиденциальной записей.
4. Создание `dump_after_update.dmp`.
5. Удаление обеих записей.
6. Создание `dump_after_delete.dmp`.

После этого скрипт автоматически ищет контрольные строки в бинарном содержимом дампов и записывает результаты в `analysis/memory_strings_analysis.md`. Для каждой найденной строки сохраняются результат, смещение внутри дампа и кодировка.

### 10.3. Результаты анализа

По результатам последнего запуска установлено:

| Дамп | Публичные данные | Конфиденциальные данные | Вывод |
|---|---|---|---|
| После создания | Исходные значения найдены, обновлённые не найдены | Исходные значения найдены, обновлённые не найдены | Введённые значения находятся в памяти процесса |
| После обновления | Исходные и обновлённые значения найдены | Исходные и обновлённые значения найдены | Старые данные не исчезают мгновенно после замены |
| После удаления | Исходные и обновлённые значения найдены | Исходные и обновлённые значения найдены | Удаление записи из репозитория не гарантирует немедленное физическое удаление строк из памяти |

Полная таблица с фактическими смещениями находится в `analysis/memory_strings_analysis.md`.

### 10.4. Почему конфиденциальные данные всё равно видны в памяти

Шифрование защищает данные внутри хранилища, но не может скрыть их в момент обработки. Для отображения записи пользователю приложение должно выполнить расшифровку:

```text
ciphertext в репозитории
        ↓
расшифровка application-слоем
        ↓
plaintext в объекте ответа
        ↓
JSON-ответ и отображение в браузере
```

В текущей реализации в `DataUseCases._to_view()` конфиденциальные название и содержимое расшифровываются перед формированием `RecordView`. Поэтому исходный текст может находиться:

- в локальных переменных;
- в объекте ответа API;
- в буферах сериализации JSON;
- во временных копиях строк Python;
- в памяти браузера после получения ответа.

Автоматический dump-тест дополнительно сохраняет последний объект ответа до следующего этапа, чтобы воспроизводимо показать наличие plaintext в памяти. Даже после удаления этой ссылки Python не обязан немедленно затереть ранее использованные области памяти. Поэтому старые строки могут оставаться в heap и попадать в дамп.

Это не означает, что шифрование бесполезно. Внутри `InMemoryDataRepository` конфиденциальные поля хранятся как ciphertext. Шифрование защищает данные от простого чтения структуры репозитория и было бы особенно полезно для базы данных, файла или резервной копии, если ключ хранится отдельно. Однако полный дамп процесса является более сильной моделью угроз: в нём потенциально могут находиться и plaintext, и объект шифровальщика с ключом.

### 10.5. Отличие публичных и конфиденциальных данных

Публичные данные хранятся в репозитории открытым текстом, поэтому их исходные строки могут находиться в дампе непосредственно как элементы словаря.

Конфиденциальные данные в репозитории хранятся зашифрованными, однако расшифрованные копии появляются во время выполнения application-логики и формирования ответа. Таким образом, отличие заключается не в гарантированном отсутствии plaintext в памяти, а в том, что конфиденциальные данные защищены на этапе хранения и требуют специального доступа к ключу или выполнения кода расшифровки.

### 10.6. Как можно уменьшить риск

Полностью исключить plaintext из дампа невозможно, если сервер должен самостоятельно расшифровать данные и отправить их пользователю. Однако риск можно уменьшить:

1. Не хранить расшифрованные `RecordView` и ответы дольше времени, необходимого для отправки ответа.
2. Не сохранять plaintext в глобальных переменных, кэше и журналах.
3. Использовать минимальное время жизни временных объектов.
4. Для низкоуровневых буферов использовать изменяемые массивы байтов и затирать их после обработки. В Python это ограничено, поскольку строки могут копироваться интерпретатором и библиотеками.
5. Запретить создание дампов для обычных пользователей и ограничить права доступа к файлам дампов.
6. Разделить сервисы и ключи, чтобы компрометация одного процесса не раскрывала все данные.
7. Использовать аппаратно защищённые области памяти или изолированный сервис расшифровки, если требуется более сильная защита.
8. Применять клиентское шифрование, при котором plaintext расшифровывается только в браузере, а сервер вообще не получает исходное содержимое.

Клиентское шифрование обеспечивает наиболее сильную защиту от дампа памяти сервера, но меняет архитектуру приложения: сервер уже не сможет самостоятельно выполнять поиск, анализ или просмотр содержимого конфиденциальных данных.

### 10.7. Итог по дампам

Эксперимент подтвердил, что Fernet защищает конфиденциальные данные внутри in-memory-репозитория, но не гарантирует их отсутствие в полном дампе процесса. Для отображения пользователю данные должны быть расшифрованы, а управление памятью Python не обеспечивает гарантированное мгновенное затирание всех копий. Поэтому безопасность конфиденциальных данных состоит из двух разных уровней:

- защита данных при хранении — обеспечивается Fernet-шифрованием;
- защита данных во время обработки — ограничена особенностями Python, жизненным циклом объектов и правами доступа к процессу.
